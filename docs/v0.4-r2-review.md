## F1. Widget index is re-walked per frame; the moduledoc oversells it

`WidgetIndex.collect/1` runs in `render_unsafe/1` on **every render** —
i.e. every keypress that changes anything, every cmd result, every sub
tick — not "once." `maybe_route_widget` reads the *previous* frame's
index at key-dispatch time, which is correct (tree is unchanged at that
point), but the `WidgetIndex` moduledoc claims it avoids "re-walking the
tree on every keypress" — that's describing a non-benefit. The real cost
is one extra full tree walk per frame, alongside the `Focusables.collect/1`
walk that *already happens on the same tree in the same function*.

For a viewport-only index this is cheap and fine. But it will not stay
viewport-only — after generalization every focusable input contributes,
and nobody will revisit the cost because the comment says it's handled.

**Fix — pick one:**

- **Preferred:** fold widget-index collection into `Focusables.collect/1`.
  It already walks the identical tree for the identical reason (finding
  focusable elements). Return both the focusables list and the
  `%{focus_id => element}` auto-route map from one walk. Two walkers over
  one tree for one purpose is the smell.
- **Minimum:** if folding is more disruptive than it's worth right now,
  just make the `WidgetIndex` moduledoc honest: "Re-walked once per frame
  in `render_unsafe/1`, alongside `Focusables.collect/1`. Cost is O(tree);
  acceptable while the auto-routed set is small. Fold into `Focusables`
  if the walk ever shows up in `[:harlock, :frame, :render]` telemetry."

Either is acceptable. A misleading moduledoc is not.

## F2. `Keyword.fetch!` in `maybe_route_widget` can crash the runtime

In `maybe_route_widget/2`:

```elixir
offset = Keyword.fetch!(el.opts, :offset)
content_height = Keyword.fetch!(el.opts, :content_height)
```

If an app writes `viewport(focusable: :log, child: ...)` and omits
`offset:` or `content_height:`, `fetch!` raises a `KeyError` **inside the
runtime process, on the `handle_info` path** — not inside the user's
`update/2`. That is a spine crash: it takes the supervision tree through
teardown, and the stack trace points at `runtime.ex`, not at the app's
`view/1` where the actual mistake is.

This matters more after generalization: `TextBuffer` widgets have more
required opts, so more apps will trip this.

**Fix:** routing must **degrade to `:pass`** on missing/invalid opts —
deliver the raw key, let the renderer or the app surface the misuse.
Replace the `fetch!` calls with `Keyword.fetch/2` and treat `:error` (or
a missing value) as `:pass`. The `with`/`else` in `maybe_route_widget`
already has a `:pass` exit — route the failure there. The runtime never
faults on app opt mistakes.

Apply the same safe pattern in the Tabs and TextBuffer generalization —
do not copy `fetch!` three times.

## F3. `widget_metrics` stale-frame safety is correct but undocumented

`maybe_route_widget` reads `state.widget_metrics[focus_id][:viewport_h]`,
which is recorded during the *previous* render. This is **not a bug** —
every focus-changing path (`maybe_handle_focus` returning `{:handled,…}`,
any `update/2` that moves focus) renders before the next key event is
processed, so the metrics are always fresh-enough for the focused widget.
The render-after-every-handled-event discipline is what closes the hole.

But it is load-bearing and invisible. The next person to touch the
runtime could "optimize away" a render on some path and silently break
page-step / `:end` clamping (it would fall back to `state.rows`, wrong
for any viewport shorter than the screen).

**Fix:** one comment at the `viewport_h` read in `maybe_route_widget`,
stating the invariant explicitly — something like: "Safe to read
last-frame metrics: every focus-changing path renders before the next
key event, so the focused widget's metrics are current. If you add a
focus path that doesn't render, this clamping breaks." No code change.

## F4. The `{:harlock_*}` routed-message tuples are public API — document them

`{:harlock_scroll, focus_id, new_offset}` (and the forthcoming
`{:harlock_tab_change, focus_id, new_index}` /
`{:harlock_edit, focus_id, {new_value, new_cursor}}`) are pattern-matched
by every app's `update/2`. That makes them public contract surface — the
same category as `{:harlock_event, _}` — and a 1.0 API freeze will lock
them.

The widget-specific shape (vs. a unified `{:harlock_widget, id, payload}`)
is the **right** call — keep it. Unified would force every app into a
nested `case` on payload shape, which is exactly the boilerplate R2
exists to delete. No change to the shape.

**Fix:** in the *same commit* as the Tabs/TextBuffer generalization, add
all three tuples to wherever the runtime's event-message vocabulary is
documented for app authors (alongside `{:harlock_event, _}` — likely
`Harlock.App` docs or the README event section). Not "later." An app
author needs to know these exist to write the `update/2` clause.

## Box-as-focus-proxy — Phase 1 touch-up, NOT v0.4.1

Separate from F1–F4. The prototype status report correctly scoped the
`box(focus_proxy: :child_id)` *mechanism* out of v0.4. That mechanism is
genuinely v0.4.1.

But there is a v0.4 consequence the report under-weighted: pre-R2, apps
focused the wrapping `box` and its border highlighted. Post-R2, focus is
on the inner `viewport`, so the box border goes visually dead. In
`examples/overview.exs` — the R1 example whose entire job is to look
correct for new users — that reads as "the focused thing isn't
highlighted." Shipping the adoption release with a demo that looks less
focused than the v0.3 showcase is not acceptable.

**Fix (Phase 1 scope, small):** give `examples/overview.exs` explicit
visual focus indication that survives R2 — e.g. the example styles the
box border conditionally off `Focus.current()`/`Focus.focused?/1`. This
is example code using existing API, not a framework feature. It keeps
the R1 deliverable looking right.

The general `box(focus_proxy:)` mechanism stays a v0.4.1 roadmap item —
add it to the v0.4.1 list when release-prep writes that ROADMAP section,
with a back-reference to this note so the motivation survives.
