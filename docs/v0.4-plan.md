# v0.4 implementation plan — for Claude Code

Status: planning. Source-of-truth for the v0.4 cycle.
Companion docs: `docs/feedback-v0.3.md` (motivation), `ROADMAP.md` (long arc).

---

## TL;DR for the executor

v0.4 is the **"adoption"** release. Its job is to make Harlock *cost less
to use*, not to grow the feature count. This is a deliberate departure from
the feature list in `ROADMAP.md`'s v0.4 section — see "Scope decision"
below. Read `docs/feedback-v0.3.md` first; it is the entire justification.

Three work items, in strict order:

1. **R1** — runnable, CI-compiled end-to-end README example. (~1 day)
2. **R2** — focus-aware key routing for stock widgets. (~1 week, the spine)
3. **Theming** — full token set + style cascade. (parallel-safe, secondary)

Plus **R3**, a measurement gate that defines "R2 is done."

Deferred to v0.4.1 (NOT this cycle): `tree` / `menu` / `select` widgets,
multi-line `text_area`, the non-pubsub `Sub` kinds. Reasoning in
"Deferred" below — short version: building new widgets *before* R2 means
building them against the old contract and rewriting them immediately.

---

## Scope decision (read before objecting to the cut)

`ROADMAP.md`'s v0.4 section lists four feature items: full theming, style
cascade, `tree`/`menu`/`select`, multi-line `text_area`. The v0.3 feedback
doc — written by the first real consumer, the audience an "adoption"
release exists for — names **none** of those four as a pain point. The two
gaps it does name are G1 (no end-to-end example) and G2 (widgets don't own
key handling → 30–40% boilerplate).

So the roadmap's v0.4 is feature-growth wearing an adoption label. This
plan re-scopes v0.4 around the feedback and moves the four feature items
to a new v0.4.1. Theming survives into v0.4 because it is cheap, low-risk,
visible, and does not conflict with R2 — but it is demoted from headline
to secondary track.

Do not silently re-expand scope back to the roadmap's list. If the cut
seems wrong, raise it with the maintainer — do not just implement the
widgets.

## Branch & process

- Single branch `v0.4-dev` off current `main` (which is at tag `v0.3.0`,
  commit on `mix.exs` `@version "0.3.0"`).
- One reviewable commit per phase below. Conventional, imperative commit
  subjects consistent with existing history (e.g. `Add end-to-end README
  example`, `Focus-aware key routing: Viewport prototype`).
- **CI must be green on every commit**, not just at the end. The existing
  `.github/workflows/ci.yml` runs format check, warnings-as-errors
  compile, `mix test`, Credo `--strict`, Dialyzer. No commit lands red.
- Do **not** bump `@version` or write the `CHANGELOG.md` `[0.3.0]→[0.4.0]`
  entry until the release-prep phase. The `[Unreleased]` slot is where
  in-progress notes accumulate.
- Do **not** tag. Tagging is a maintainer action after sign-off.

## Phase 1 — R1: end-to-end README example

**Goal:** one runnable app that shows table + viewport + scrolling + focus
+ one `Cmd` round-trip working *together*. Per `feedback-v0.3.md` G1, ~80%
of new-user questions are about wiring widgets together, not the widgets
themselves.

**Deliverable:** a real example file — `examples/overview.exs` (naming
consistent with the existing `counter` / `sysmon` / `showcase` examples) —
and the same code embedded in `README.md` between the `Counter` snippet
and `## Installation`. The README copy and the file must not drift; if
keeping them byte-identical is painful, the README shows the example and
the prose says "full source: `examples/overview.exs`" — but the *whole*
app must appear in the README, that is the point.

**Hard requirement — it compiles in CI.** An uncompiled README example
rots silently and is worse than none. Acceptance, from `feedback-v0.3.md`
R1:

- Compiles as part of `mix test` (a test that `Code.compile_file/1`s the
  example, or a doctest harness — executor picks the lighter mechanism).
- Exercises: `Focus` traversal (`Tab`/`Shift-Tab`), viewport scrolling via
  `Harlock.Viewport.apply_key/4`, a `table` with row selection, and at
  least one `Cmd` round-trip (`Cmd.from/1` → `{:harlock_event, _}` →
  `update/2`).
- Each G1 gotcha is demonstrated *by correct idiom*, not by a call-out
  comment: `text/1` is single-line; a column `:render` returns
  `String.t()` not an `Element`; the `apply_key` helpers exist.

**Keep it honest:** this example is written against the **v0.3** API and
lands *before* R2. After R2 ships, this example is the natural place to
show the new key-routing — but in this phase it uses today's idioms. Do
not block R1 on R2.

**Scope guard:** ~50 lines of app code. If it sprawls past ~80, the
example is doing too much — cut a feature, not the compile test.

## Phase 2 — R2: focus-aware key routing (the spine)

**Goal:** a focused stock widget handles its own navigation keys without
the app's `update/2` containing the routing boilerplate. This is the item
that addresses G2 and the "30–40% boilerplate" figure.

### Decided design (do not re-litigate without the maintainer)

**The widget returns a message that the app's `update/2` still sees.** It
does **not** mutate model state directly.

Rationale: TEA single-source-of-truth is the property that makes Harlock
attractive to Phoenix devs and keeps every widget headless-testable
(`ROADMAP.md` principle 4). A widget that silently mutates the model
breaks both. The extra plumbing is the price and it is worth paying. The
"mutate directly" option from `feedback-v0.3.md` R2 is explicitly
rejected.

Concretely: the runtime already knows `Focus.current()`. When a key
arrives and the focused element opted into key handling, the runtime
calls that widget's pure `apply_key` helper, and delivers the *result*
to `update/2` as a normal message (shape consistent with existing event
messages — align with whatever `{:harlock_event, _}` / `{:key, …}` shape
the runtime already uses; the executor inspects `runtime.ex` and the
parser to pick the exact tuple, and documents the choice in the commit).
The app's `update/2` still sees it, still owns the model write. Less
boilerplate, same single source of truth.

### Process — prototype narrowly first

This is a **runtime-contract change**. `ROADMAP.md`'s "Notes for whoever
picks this up" warns twice that the runtime is the spine and must not
accumulate state casually. `feedback-v0.3.md` R2 warns contract changes
blow their estimates. Therefore:

1. **Prototype against `Viewport` only, end-to-end**, before touching
   anything else. Viewport's key set (`:up`/`:down`/`:page_up`/
   `:page_down`/`:home`/`:end`) is small and well-understood, and
   `Harlock.Viewport.apply_key/4` already exists as the pure core — R2
   is *routing into it*, not rewriting it.
2. Get CI green and the contract reviewed at the Viewport-only stage.
   **Stop here and check in with the maintainer before generalizing.**
3. Only then generalize the same mechanism to `Tabs`
   (`Harlock.Tabs.apply_key/3`) and `text_input`
   (`Harlock.TextBuffer.apply_key/3`).

### Design questions to resolve in the prototype (from feedback R2)

- **Opt-out.** A widget must be able to decline auto-routing (e.g. a
  viewport inside a modal with custom keybindings). Plan: an explicit
  element option, `handle_keys: false` (default `true` for widgets that
  have an `apply_key` helper). Confirm the option name and default
  during the prototype; document in the element's docs.
- **Opt-in surface.** Decide whether auto-routing is on-by-default for
  the three stock widgets or requires `handle_keys: true`. Default-on is
  the better adoption story (zero key code for stock widgets — the whole
  point of R2); default-off is safer for existing apps. Lean default-on,
  but this is a real back-compat call — flag it for the maintainer with
  the migration cost spelled out (existing apps that *also* handle these
  keys in `update/2` would now double-handle). If default-on, the v0.4
  CHANGELOG `Changed` section must call this out as a behavior change.
- **Focus interaction.** The runtime already resolves `Focus.current()`;
  R2 is plumbing that into key dispatch. No new focus state.

### Tests

- Headless (`IO.Test` backend) per `ROADMAP.md` principle 4. A focused
  viewport scrolls on `PgDn` with the app's `update/2` containing **zero**
  scroll-routing code. Same for `Tabs` left/right, same for `text_input`
  insert/backspace.
- An opt-out test: `handle_keys: false` viewport does *not* auto-scroll;
  the app sees the raw key.
- The crash-path discipline still applies — no new IO path, so low risk,
  but if the runtime gains a field, the `smoke_crash/0` template still
  must pass.

## Phase 3 — Theming: full token set + style cascade (secondary track)

Parallel-safe with R2 (no runtime-contract overlap). Can be its own
commit landed before or after R2. Spec is already concrete in
`ROADMAP.md` v0.4 — follow it:

- Add the remaining `Harlock.Theme` tokens: `primary`, `accent`, `muted`,
  `error`. The four existing tokens (`header`, `focus`, `selection`,
  `border`) and `Theme.get/1` ship since v0.2 — extend, don't rebuild.
- Built-in themes: `:default`, `:dark`, `:high_contrast`. `:default` must
  stay byte-identical to today's output (golden-frame test, same
  discipline as the v0.2 theme work).
- Auto-downgrade truecolor → 256 → 16 based on `Caps`.
- Style cascade: `box` propagates `:border_style` to title; `table`
  accepts `:header_style` / `:row_style` / `:alt_row_style` /
  `:selected_style` / `:focus_style` (all defaulting to theme);
  `Style.merge/2` inheritance (child overrides parent, unspecified attrs
  inherit — `Style.merge/2` already exists from v0.2, verify it has the
  inheritance semantics or extend it).

**Scope guard:** no *new widgets* in this phase. Theming touches existing
renderers only. If a `tree`/`menu`/`select` need appears, that is the
v0.4.1 signal — stop and note it, don't build it.

## Phase 4 — R3: the boilerplate KPI (the "R2 is done" gate)

`feedback-v0.3.md` R3: the 30–40% boilerplate figure is the KPI. Before
R2, count the lines of `update/2` in `examples/showcase.exs` that exist
*purely* to wire `apply_key` helpers (receive key → check focus → look up
widget state → call helper → write back). Record the number in the commit
message. After R2, recount. **R2 is not done until that count roughly
halves.** If it doesn't, R2 missed G2 — reopen Phase 2, don't ship.

Also: migrate `examples/showcase.exs` itself to the R2 mechanism (it is
the most key-handling-heavy example — best demonstration and best KPI
subject). The R1 `overview.exs` example may also be updated to the new
idiom here, now that R2 exists.

## Deferred to v0.4.1 — do not build this cycle

- `tree` / `menu` / `select` widgets.
- Multi-line `text_area`.
- `Sub.file` / `Sub.signal` / `Sub.port`. (`Sub.pubsub` is also roadmapped
  for v0.4 — it is small and high-value for Phoenix users, but it is
  *not* in this plan's scope either; if the maintainer wants it pulled
  in, it is an independent add. Default: defer with the rest.)

**Why deferred, not dropped:** these are real and roadmapped. But building
three new stock widgets *before* R2 means building their key handling
against the old contract and rewriting it the moment R2 lands — you would
manufacture the exact boilerplate R2 exists to delete. New stock widgets
should be the *first consumers* of the focus-routing contract. They make a
better v0.4.1 for waiting one cycle.

## Risk register

- **R2 estimate explodes.** Most likely failure mode; it is a
  runtime-contract change. Mitigation: the Viewport-only prototype gate
  (Phase 2 step 2). If the prototype fights past its estimate, the
  fallback is to **ship v0.4 as R1 + theming and push R2 to v0.4.x** —
  this is a planning-time decision, make it the moment the prototype
  slips, not in a panic later. v0.4 with just R1 + theming is still a
  legitimate release; R1 alone clears the single biggest feedback gap.
- **Scope creep back to the roadmap's widget list.** Mitigation: the
  "Scope decision" and "Deferred" sections above. Executor must not
  re-expand silently.
- **Default-on key routing breaks existing apps.** Real back-compat
  surface (`counter`/`sysmon`/`showcase` and any external consumer).
  Mitigation: the maintainer makes the default-on/off call explicitly in
  Phase 2; whichever way it goes, the CHANGELOG documents it.
- **README example drift.** The example exists in two places (file +
  README). Mitigation: the CI compile-check is on the *file*; the README
  must quote that file verbatim. If drift keeps happening, collapse to
  "README points at the file" — but the example body still belongs in
  the README per G1.
